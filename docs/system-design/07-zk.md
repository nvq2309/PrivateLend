# ZK and Merkle System

```mermaid
flowchart TD
  subgraph Overview
    S[Secret Note Data] --> W[Witness]
    W --> P[ZK Prover (SnarkJS + Groth16)]
    P --> V[Groth16 Verifier (syscalls)]
  end
  subgraph Detail
    C[Commitment (Poseidon)]
    N[Nullifier (Poseidon)]
    R[Merkle Root (Poseidon)]
    PI[Public Inputs]
  end
  S --> C --> PI
  S --> N --> PI
  R --> PI --> P
  V --> C
```

Statement being proven
- The prover knows a valid note whose commitment is in the Merkle tree.
- The nullifier is derived from the note and has not been spent.
- The new commitment is correctly derived from the note update.

Public inputs (binding)
- Merkle root, nullifier hash, current commitment, new commitment.
- These inputs bind the proof to a specific vault and root.

Artifact/version binding
- Proof artifacts are versioned; proofs must match the active verifying key.
- Mismatch must be surfaced to UI and trigger re-prove.

Security assumptions
- Trusted setup for Groth16 is assumed uncompromised.
- Poseidon parameters are consistent across implementations.

Merkle policy
- Current root is accepted today; near-term add a root history window.
- Root drift is a critical correctness risk; indexer must reconcile.
